# 金幣定位進度

2026-10-09，對 profile.json SHA-256 所綁定的 JP 客戶端進行唯讀定位，角色為 190cm。0.4.4 已接入正式監測的金幣總額與本次淨變化。

## 實測變化

使用者提供遊戲畫面金幣總額，依序為 293 → 296 → 299。
在同一個已核對啟動時間及角色名稱的程序中，最初搜尋得到 3595 筆候選，兩次變化比對後剩同一個位址的 16 位元及 32 位元讀法：

```text
PID: 56892
啟動時間 UTC ticks: 639271300314175350
候選地址: 0x11DB4520
讀值: 293 → 296 → 299
目前角色物件: 0x11DB4508
金幣候選相對偏移: +0x18
```

上述 PID 與 heap 地址僅記錄實測，不得寫入正式讀取設定。

## 指標路徑

使用既有、已驗證角色名稱及職業的目前角色指標，實測解析到同一個金幣候選位置：

```text
manager = read32(mainModuleBase + 0x35B914)
actor = read32(manager + 0x78)
gold = signedRead32(actor + 0x18)
```

此次主模組基址為 0x400000。應用程式名稱確定為 190cm，與既有 actor 名稱核對來源一致。金幣來源為目前角色物件，並非經驗物件或另一個遊戲程序。

## 重新開啟後驗證

使用者重新登入 190cm，提供畫面金幣 304。新程序 PID 48988，啟動時間 UTC ticks 639271336248458971；不使用舊地址，從主模組相對根重新解析，得到角色物件 0x1727C2E8、金幣地址 0x1727C300，讀值為 304。讀取前後核對應用程式名稱及 actor 名稱均為 190cm，actor 指標及金幣值一致。實際地址已變，+0x18 路徑在這次跨程序驗證仍成立。

## 欄位寬度與程式碼證據

在同 SHA-256 的 JP 客戶端反組譯確認：

```text
0x55F651: mov edx, [0x75B914]
0x55F657: mov ecx, [edx+0x78]     ; current actor
0x55F65B: push 4                 ; attribute type 4
0x55F65D: add ecx, 0xC           ; actor attribute subobject
0x55F660: call 0x44A490

0x44A490: movsx eax, word [esp+4]
0x44A49A: movzx eax, byte [eax+0x44A4DC]
0x44A4A1: jmp dword [eax*4+0x44A4C8]
type 4 -> dispatch index 1 -> 0x44A4B4
0x44A4B4: mov eax, dword [ecx+0xC]
0x44A4B7: ret 4
```

actor + 0xC 子物件內 +0xC，即 actor +0x18，明確使用 32 位元讀取。設定函式 0x44A3A0 的 type 4 分支於 0x44A3E0 將 DWORD 寫入 [ecx+0xC]，使用 signed `jge` 檢查並將負數截為 0；可按非負 signed Int32 讀取，負值應拒絕。

上述預設反組譯基址為 0x400000；正式定位須換成當下主模組基址加 RVA。此欄位已具有使用者實際金幣變化、已驗證角色來源、遊戲程式碼與重新開啟後的證據，不只依賴數值碰巧相同。

## 尚待確認與接入

- 190cm 的跨程序重新定位已實測一次；其他角色（含 moooo）的畫面金幣尚未由使用者核對。
- 正式讀取每次重新解析，核對角色名稱、指標及重讀金幣值一致；負值、讀取失敗或不一致返回 null。不得固定使用本次 heap 位址。

0.4.4 已接入目前金幣及本次淨變化。停止保留舊資料並標示已停止更新；重新開始同步並重設金幣基準。未知端點的淨變化保持 null，不補示範金幣。

開發建置與 0.4.4 成品均實測 190cm 的 304、5 秒取樣、停止後不更新及重新開始淨變化歸零。原生測試涵蓋 70000（避免 16 位元截斷）、0、Int32 上界、負值、名稱不符、指標替換及讀取途中變動；統計測試涵蓋收入、支出與未知基準。其他角色仍未由使用者提供畫面金額核對。
